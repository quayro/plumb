# Optional Rust adapter

This adapter adds Rust source policy without a Rust toolchain and without a dependency in Plumb's core. It is built on the [adapter SDK](../sdk/README.md) and needs Node 22.18 or newer. Formatting, linting and compilation are the core's `rust` profile, which runs rustfmt and clippy; a project with that profile runs this adapter beside them when the registry lists it.

## Installation

Keep the adapter and its registry outside the candidate repository:

```sh
node tools/plumb/packages/rust/adapter.ts --manifest > "$HOME/.local/share/plumb-rust/registry.json"
```

The manifest pins the Node binary, the adapter and the SDK by SHA-256. Add a project that selects the adapter and pass the registry:

```json
{
  "schemaVersion": 1,
  "preset": "portable",
  "projects": [
    {
      "root": ".",
      "profile": "rust",
      "options": {
        "forbiddenImports": [{ "path": "std::process", "reason": "Use the reviewed runner" }]
      }
    }
  ]
}
```

```sh
plumb check --adapters "$HOME/.local/share/plumb-rust/registry.json"
```

## Options

`forbiddenImports` is a list of `{ "path", "reason" }` entries. A `path` is a Rust path such as `std::process`, optionally with a leading `::`. `core` and `alloc` count as `std`, and the entry forbids the path and every item beneath it. Without `forbiddenImports` the `rust/import` rule does nothing.

## Checks and limits

| Rule             | Behavior                                                                                                                |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `rust/directive` | `allow`, `expect` and `rustfmt::skip` attributes, inner or outer, including inside `cfg_attr` at any depth              |
| `rust/import`    | any way of naming a forbidden path: `use`, trees, globs, renames, `pub use`, `extern crate`, leading `::`, inline paths |
| `rust/skip`      | `#[ignore]` and `#[ignore = "..."]`, including through `cfg_attr`; `#[cfg(...)]` gates that are always false            |
| `rust/input`     | a source that cannot be read, does not match its hash, or cannot be tokenized (incomplete)                              |

The adapter tokenizes each file. Comments (nested block comments included), string, byte, C and raw strings with any number of hashes, and character literals are whole tokens, so text inside them is never read as code. Lifetimes such as `'a` are told apart from characters such as `'a'`. An unterminated literal or comment is incomplete.

`rust/directive` matches the attribute wherever whitespace or comments fall between its tokens, so `# [ allow ( dead_code ) ]` is refused. Clippy's own `clippy::` attributes are not suppressions and are not refused; a suppression written as `allow(clippy::...)` is.

`rust/import` resolves the `use` declarations of one file. It follows a renamed prefix (`use std as s;` then `s::process::Command`), a `core` or `alloc` path, and a name bound by `extern crate`. Each of these is incomplete rather than a pass:

- a glob of a strict prefix of the forbidden path, such as `use std::*;`
- a glob of a path this file cannot resolve, such as `use super::*;` or `use crate::prelude::*;`
- a path built from a macro variable, such as `$p::new()` in a macro body
- `paste!`, `concat_idents!` and `include!`, which build or splice code this file does not show
- a use tree that is not a plain path, such as `use $p;`, which is unreadable input

A glob import of a path beneath the forbidden one, or the forbidden path itself, is a violation at the glob.

`rust/skip` decides `cfg` predicates only from their tokens: `any()`, `all()`, `not(...)`, `true` and `false`, and the combinations of them. A predicate that names a feature, a target or `test` is undecided and is not reported. A `cfg` inside `cfg_attr` is not reported, since its predicate may be false; an `ignore` inside `cfg_attr` is always reported.

It reads tokens, not types, and it does not follow:

- a forbidden type reached without a name, such as a value returned by a function in another file
- a name that another file re-exports from the forbidden path; that file's own `use` of the forbidden path is a violation, so the policy still fails there
- attributes produced by a macro from another crate
- code generated by a build script, or the files a `mod x;` declaration loads, which are checked only as their own files

Only `rust/import` can be excepted. Run `cargo clippy` and the tests as a [verification suite](../../docs/guides/verification.md) for what needs the compiler.
